## New finding: a signaled timeline value is not automatically a whole-submission retirement fence
`vkQueueSubmit2` permits `VkSemaphoreSubmitInfo::stageMask = VK_PIPELINE_STAGE_2_VERTEX_SHADER_BIT` for a signal. That signal's first scope does **not** necessarily include later fragment/color-output stages. Thus `vkGetSemaphoreCounterValue >= N` proves completion of the signal's **declared scope**, not necessarily completion of *every GPU operation referencing the resources retained by submission N*. Using such a value to drop all submission references can be unsound.

For a general-purpose retirement marker that covers the whole batch and preceding work on the queue, submit the timeline signal with `VK_PIPELINE_STAGE_2_ALL_COMMANDS_BIT`. For legacy `vkQueueSubmit`, signal operations have the older whole-submission semantics. A narrowly scoped signal can still be valid for other purposes, but must not be misclassified as a full-submission completion marker.

## Second finding: completion semaphores need signal provenance
`vkSignalSemaphore` can advance a timeline semaphore from the host. Therefore an arbitrary counter value is not proof of GPU work unless the host can establish that the corresponding value was generated by a correctly scoped **queue submission**, not by an unrelated host signal or a different queue. Reserve dedicated per-queue retirement timelines; prohibit host signals and external imports into those semaphores; record a successful queue-submit result and its signal value before admitting a completion record. Preserve the distinction between a submit attempt and a successful submission; a failed submission does not earn a completion value.

The Vulkan spec also requires valid signal ordering and increasing timeline values. In a multi-queue design, independently owned retirement timelines avoid implicit cross-queue signal-order assumptions. A cross-queue wait or memory barrier is a separate correctness obligation; completion bookkeeping alone is not a visibility or ownership transfer.

## Proposed host interface (hypothesis / design)
```cpp
struct CompletionTicket {
    QueueId queue;
    uint64_t signalValue;
    // Only issued by the submission layer for a successful VkQueueSubmit2
    // with a dedicated timeline semaphore and ALL_COMMANDS signal scope.
};
```
- Submission adapter owns creation and signaling of each queue's retirement timeline.
- Adapter validates `signal.stageMask == VK_PIPELINE_STAGE_2_ALL_COMMANDS_BIT` for tickets; other signals cannot issue retirement tickets.
- Record ticket and retained resources only after successful `vkQueueSubmit2`; failed submits enter an explicit failure/recovery path, never synthetic completion.
- Poll `vkGetSemaphoreCounterValue` on the same timeline and retire tickets at or below the observed counter; maintain references for other queues independently.
- Device-loss paths do not infer idle from failed polling. Destruction policy must follow Vulkan's device-loss/teardown rules separately.
