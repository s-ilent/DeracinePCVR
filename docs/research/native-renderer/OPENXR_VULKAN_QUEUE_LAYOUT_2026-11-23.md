**Date:** 2026-11-23. **Scope:** one new normative-source audit, not a GPU/runtime experiment. **Branch:** `research/native-openxr-vulkan-queue-layout-contract-20261123`; parent `773bb41d0670755eaa3d753737f8fa587518a248`. ## New question

The preceding NRI barrier report left the **actual OpenXR Vulkan image entry/exit layout and queue ownership** unresolved. What does the Vulkan OpenXR binding normatively require, and does `xrReleaseSwapchainImage` require a CPU-side wait for GPU completion?

The host should create Vulkan instance/device through the enable2 functions and **then** let NRI adopt those handles, rather than ask NRI to independently create a device.
2. [Lines 338–398](https://github.com/KhronosGroup/OpenXR-Docs/blob/18ebc0374da23c020ef4c949f9b144ffae6160ef/specification/sources/chapters/extensions/khr/khr_vulkan_enable2.adoc#L338-L398): the application selects a **graphics-capable queue** and supplies its family/index in `XrGraphicsBindingVulkan2KHR`; the Vulkan instance/device must come from the enable2 creation functions and physical device must match the runtime-selected one. Runtime may use that queue or a queue in another logical device.
3. [Lines 400–419](https://github.com/KhronosGroup/OpenXR-Docs/blob/18ebc0374da23c020ef4c949f9b144ffae6160ef/specification/sources/chapters/extensions/khr/khr_vulkan_enable2.adoc#L400-L419): **shared queue external synchronization** is required across Vulkan submissions and the four OpenXR calls that may access the bound queue: `xrBeginFrame`, `xrEndFrame`, `xrAcquireSwapchainImage`, `xrReleaseSwapchainImage`. `xrWaitSwapchainImage` is not in this list. A Vulkan submission mutex covering only the renderer's own calls is insufficient.
4. [Lines 461–487](https://github.com/KhronosGroup/OpenXR-Docs/blob/18ebc0374da23c020ef4c949f9b144ffae6160ef/specification/sources/chapters/extensions/khr/khr_vulkan_enable2.adoc#L461-L487): **after a successful wait** (`XR_SUCCESS` or `XR_SESSION_LOSS_PENDING` as explicitly named by this extension), the image is in a layout **compatible with** `VK_IMAGE_LAYOUT_COLOR_ATTACHMENT_OPTIMAL` (color) or `VK_IMAGE_LAYOUT_DEPTH_STENCIL_ATTACHMENT_OPTIMAL` (depth), and the bound queue **owns** it. At release, the runtime interprets the image as having that compatible layout and queue ownership. The application is responsible for restoring both before release.
5. [Lines 479–493](https://github.com/KhronosGroup/OpenXR-Docs/blob/18ebc0374da23c020ef4c949f9b144ffae6160ef/specification/sources/chapters/extensions/khr/khr_vulkan_enable2.adoc#L479-L493): **release is explicitly compatible with GPU command buffers submitted on the bound queue that have not yet finished execution**. Therefore a blanket `vkQueueWaitIdle` or fence wait **before every release is not a normative requirement**. Commands must be correctly submitted and ordered; destruction still requires safe completion. This corrects the overly conservative implication in earlier proposed test plans, without claiming that all runtime synchronization problems are solved.
6. [Lines 495–531](https://github.com/KhronosGroup/OpenXR-Docs/blob/18ebc0374da23c020ef4c949f9b144ffae6160ef/specification/sources/chapters/extensions/khr/khr_vulkan_enable2.adoc#L495-L531): OpenXR swapchain usage bits constrain Vulkan image usage. Native host must request attachment/storage/transfer/sampled capabilities it actually needs; NRI wrapping does not add missing usage flags.

## Consequences for the host/NRI contract

- **Host owns the OpenXR Vulkan session and graphics queue.** Its queue synchronization guard must cover the four OpenXR functions above **and** host/NRI Vulkan queue operations on the same queue. Never let NRI and the OpenXR frame loop concurrently access the queue unsynchronized.
- **Waited-image entry state is specified by OpenXR**, not `UNDEFINED` and not an unknown inherited NRI state. Use the attachment-compatible entry layout and bound-queue ownership as the host's barrier baseline. The word *compatible* matters; avoid asserting that the implementation has supplied an inspectable, byte-for-byte `VkImageLayout` enum state.
- **Release state is specified too.** If rendering changes layout or queue ownership, restore attachment-compatible layout and bound-queue ownership before release. If the image remains an attachment on the bound queue, a redundant external-queue ownership transfer is **not** justified. NRI's `EXTERNAL_QUEUE` sentinel is an available mechanism, not an OpenXR mandate.
- **Do not stall the queue per frame by default.** Finish recording/submitting image-referencing work before release; the spec explicitly contemplates unfinished submitted commands. Maintain completion tokens for safe wrapper/image-view/swapchain teardown and any other resource reuse that actually requires completion.
- **Handle wait result carefully.** The generic swapchain protocol report's `XR_TIMEOUT_EXPIRED` warning remains valid. This Vulkan extension also explicitly names `XR_SESSION_LOSS_PENDING` as a state for which it guarantees the entry layout/ownership; do not confuse this with a blanket `XR_SUCCEEDED` permission to draw. How a session-loss path should proceed is a separate application policy.

## Minimal falsifiable contract test

Build an asset-free native Vulkan/OpenXR host with a **single shared-queue lock** instrumented around `xrBeginFrame`, `xrEndFrame`, `xrAcquireSwapchainImage`, `xrReleaseSwapchainImage` and all `vkQueueSubmit*` operations on the bound queue. Create instance/device via enable2, adopt them into NRI, enumerate and wrap swapchain images. For each successful wait, record expected attachment-compatible entry state and bound queue family; draw using that state, submit, release **without a per-frame queue idle**, and retire work asynchronously. Exercise both color and depth swapchains if supported. Validate teardown waits for outstanding image-referencing submissions. A test variant that temporarily changes an image to `TRANSFER_DST_OPTIMAL` must transition it back before release. Do not intentionally violate the runtime contract in a production headset session.

**Pass:** correct device/queue binding, zero Vulkan/OpenXR validation errors, queue guard shows no overlapping bound-queue accesses, and no premature destruction. **Fail:** queue race, missing layout restoration, wrong queue family or invalid image usage. **Not tested in this run:** real runtime availability, enabled device feature negotiation, NRI device-adoption behavior under a live runtime, and game shader/RHI recovery.

## Architectural boundary and limitations

This closes a *normative contract gap* left by the previous NRI barrier report. It is **not** a UE4-level RHI discovery or a native Déraciné frame. The actual UE4 resource lifecycle, PC shader production and non-rendering game/runtime systems remain independent unsolved problems. No game binary, shader bytes, emulator graphics code, PM4/GNM logic or FPS measurements were involved. Source review only; no compiler or headset test was run.
