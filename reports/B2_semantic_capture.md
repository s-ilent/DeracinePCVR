## Finding

The best source-confirmed, pre-packet observation seam is the HLE entry for `sceGnmDrawIndex`. It receives an indexed-draw API call and scalar arguments before it validates and writes a `PM4CmdDrawIndex2`. The resulting PM4 is decoded later by Liverpool and handed to the rasterizer. This is a useful low-level draw-operation candidate, but it does **not** by itself establish a UE4 `FRHICommand`/frame-graph event, and the HLE implementation has not been observed running for the pinned input. Do not label it a verified UE4 semantic event.

A previous static atlas identifies a Déraciné guest call-site candidate at VA `0x0cbbd55` targeting the `sceGnmDrawIndex` import stub at VA `0x33c81a0`, with the candidate inside FDE `[0x0cbb9c0, 0x0xcbbee5)`. The atlas records argument setup consistent with the local HLE signature. This is static byte/instruction/FDE corroboration only; it does not prove reachability in a real frame. See the pinned historical [RHI report](https://github.com/s-ilent/DeracinePCVR/blob/a44ea64a190ba20f8394ab209d16694177859798/reports/A_ue4_rhi.md#L1-L17) and [function atlas](https://github.com/s-ilent/DeracinePCVR/blob/a44ea64a190ba20f8394ab209d16694177859798/maps/A_rhi_functions.tsv#L4-L5).

## Static path and proposed observation point

1. **Title-side candidate:** the static atlas maps the candidate guest call at `0x0cbbd55` to the `sceGnmDrawIndex` import. It records argument setup compatible with `(cmdbuf, size, index_count, index_addr, flags, type)`. Because the executable is stripped and the call-site analysis is not a UE symbol map, the caller's UE4 function identity is not established.
2. **Before PM4 construction:** [`gnmdriver.cpp`](../src/src/core/libraries/gnmdriver/gnmdriver.cpp#L459-L478) defines `sceGnmDrawIndex`; after the trace-only log, validation begins at lines 463–464 and the PM4 struct is written at lines 465–474. This entry is before packet construction. The adjacent [`sceGnmDrawIndexAuto`](../src/src/core/libraries/gnmdriver/gnmdriver.cpp#L480-L492) similarly writes a `DrawIndexAuto` packet.
3. **Packet representation:** [`pm4_cmds.h`](../src/src/video_core/amdgpu/pm4_cmds.h#L297-L307) defines `PM4CmdDrawIndex2` fields for index maximum, index-buffer address, count, and draw initiator; `PM4CmdDrawIndexAuto` is at lines 318–322. These fields describe GPU draw parameters, not UE4 object/material identity.
4. **Downstream decode:** [`liverpool.cpp`](../src/src/video_core/amdgpu/liverpool.cpp#L547-L567) reads the `DrawIndex2` packet into registers and invokes `rasterizer->Draw(true)`. The `DrawIndexAuto` path is decoded at [lines 591–608](../src/src/video_core/amdgpu/liverpool.cpp#L591-L608), then invokes `rasterizer->Draw(false)`. These are post-packet observations, not the requested pre-packet seam.
5. **Submission is later:** [`sceGnmSubmitCommandBuffers`](../src/src/core/libraries/gnmdriver/gnmdriver.cpp#L2317-L2322) forwards to the workload submission function. Submission is a broad coverage anchor but occurs after individual command packets have been constructed.

### Reversible, default-off probe shape (not implemented)

Capture the guest caller VA/return site if the HLE dispatch context exposes it. ## Runner and protected-path decision

The runner review found a direct-eBoot candidate but **no route approved for launch under the current no-protected-write guardrails**:

- `tools/benchmark/runner.ps1` accepts a game directory (`-Game`, defaulting to `-ShadowRoot`) and forms `Game\eboot.bin`; it does not accept an `-Eboot` file argument ([parameter/default setup, lines 16–49; path setup, lines 121–130](../tools/benchmark/runner.ps1#L16-L49)). The documented contract requires `benchmark-shadow.json`, private status, and a manifest eboot hash ([benchmark README, lines 104–116](../tools/benchmark/README.md#L104-L116)). Before writing, the script runs `game_shadow.py` and fails closed on an invalid shadow, then explicitly writes `Game\gameproject\saved\config\ps4\engine.ini` ([runner, lines 217–238](../tools/benchmark/runner.ps1#L217-L238)). This runner therefore cannot use the protected 1.00 source directory directly and, by design, writes a game-shadow file.
- The supplied `preflight.ps1` says its snapshot detects writes but does not prevent arbitrary processes from making them ([lines 7–20](../tools/benchmark/preflight.ps1#L7-L20)). Its write guard allows the private worktree roots and declared `Game`, while denying protected locations ([lines 237–268](../tools/benchmark/preflight.ps1#L237-L268)); `shadow-policy.json` explicitly denies `D:\Temp\Deracine\1.0` ([lines 11–22](../tools/benchmark/shadow-policy.json#L11-L22)). The `path_guard.py` documentation limits prevention to the harness's own copy/delete/write operations ([lines 1–14](../tools/benchmark/path_guard.py#L1-L14)). A new private shadow would require a separately authorized provisioning step; none was created.
- **Exact direct-eBoot candidate (not run):** `tools/benchmark/headless-gameplay.ps1` accepts `-Eboot` as a file path, hashes and records it, and launches with `-g $Eboot` ([lines 24–35, 74–80, 109–110, 257–264, 370–372](../tools/benchmark/headless-gameplay.ps1#L24-L35)). Its private-output form would be:

  ```powershell
  pwsh -NoProfile -File <worktree>\tools\benchmark\headless-gameplay.ps1 `
    -Exe <private-build>\shadPS4.exe `
    -Eboot D:\Temp\Deracine\1.0\Image0\eboot.bin `
    -SavesFrom <manifest-verified-save-source> `
    -Out <worktree>\_out\headless-gameplay\semantic-b2 `
    -Lab <worktree>\_out\headless-gameplay\semantic-b2\lab `
    -Template <worktree>\pc-vr
  ```

  The script's lab is private under `Out` by default and is copied from the tracked `pc-vr` template; its own explicit lab writes target that private lab and output ([lines 55–61, 201–240](../tools/benchmark/headless-gameplay.ps1#L55-L61)). It does not invoke the shadow manifest checker, `path_guard`, or preflight/postflight, and it only records the eboot hash—it does not enforce the expected 1.00 hash or prove the guest process cannot write adjacent game files. Therefore this is a candidate harness route that leaves the shared lab and declared shadow untouched **in the script's explicit write set**, but it is not sufficient to prove the protected input remains read-only. It was not launched.

At inspection time, the expected private executable `<worktree>\build\shadPS4.exe` was absent. No build or setup was attempted. The no-launch decision is a guard-contract limitation for this run, not proof that an isolated route cannot be engineered.
